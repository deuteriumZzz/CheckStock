# CheckStock — где сейчас товар

Небольшой веб-прототип складского учёта для менеджера: сколько товара физически лежит на каждом
фулфилмент-складе (ФФ), сколько из него в резерве под FBS, что доступно и что уже в пути
(между ФФ, на склад маркетплейса по FBO, к клиенту по FBS).

**Стек:** Python 3.13, FastAPI, SQLAlchemy 2, Alembic, PostgreSQL 16, Pydantic 2, Jinja2 и
обычный JavaScript без сборки, pytest, ruff, Docker Compose.

## Запуск одной командой

Нужен только Docker.

```bash
docker compose up --build
```

Поднимется PostgreSQL, применятся миграции, загрузятся тестовые данные, и приложение откроется на
**http://localhost:8000** (Swagger: http://localhost:8000/docs). Повторный запуск безопасен: данные
не дублируются и ваши остатки не затираются. Чистый старт с нуля: `docker compose down -v`.

Тестовые данные из задания (загружаются как **приходы**, то есть сразу попадают в историю):

| Артикул | Товар | Север | Юг |
|---|---|---:|---:|
| SKU-101 | Органайзер | 10 | 6 |
| SKU-102 | Контейнер | 5 | 0 |
| SKU-103 | Корзина | 0 | 4 |

## Запуск для разработки и тесты

Нужны Docker (для базы) и [uv](https://docs.astral.sh/uv/).

```bash
docker compose up -d db                 # PostgreSQL на localhost:5433
uv sync                                 # зависимости (Python 3.11+)
uv run alembic upgrade head             # миграции
uv run python -m app.seed               # тестовые данные
uv run uvicorn app.main:app --reload    # http://localhost:8000
```

```bash
uv run pytest                           # 83 теста на настоящем PostgreSQL
uv run ruff check . && uv run ruff format --check .
```

Тесты сами создают базу `checkstock_test`, прогоняют настоящие миграции и перед каждым тестом
очищают данные, поэтому не зависят друг от друга и от порядка. Адреса БД можно переопределить
переменными окружения `DATABASE_URL` и `TEST_DATABASE_URL` (значения по умолчанию подходят для
`docker-compose.yml`, см. `.env.example`).

## Как пользоваться

Меню слева (на телефоне внизу): **Остатки**, **Ждут действия** (со счётчиком), **История**, **Склады**.

* В «Остатках» каждый товар раскрывается по складам. В строке склада маленькие значки действий:
  плюс — приход, замок — резерв FBS, грузовик — перемещение, магазин — FBO, карандаш — исправить
  остаток. Нажатие открывает панель справа с уже выбранными товаром и складом; тип операции можно
  сменить вкладками сверху, количество вводится кнопками «−/+» или «Всё».
* Кнопка «+ Операция» вверху открывает ту же панель для любого товара и склада.
* Всё, что ждёт вашего нажатия (отправить или отменить резерв, принять перемещение или FBO), собрано
  в «Ждут действия» с цепочкой статусов; на пункте меню горит счётчик.
* Склад можно добавить, переименовать и «удалить». Удаление переводит склад в архив: остатки и
  история остаются, склад помечен «АРХИВ».

## Ключевые решения

**1. Три числа и формула.** `on_hand` — физически на складе, `reserved` — часть `on_hand`,
закреплённая под активные резервы FBS, `available = on_hand − reserved`. Резерв ничего не двигает
физически, поэтому отмена резерва — это просто `reserved −= qty`, а «потерять» товар между двумя
обновлениями нельзя.

**2. «В пути» считается, а не хранится.** Товар в пути — это сумма операций в статусе `IN_TRANSIT`.
Отдельного счётчика нет, поэтому он физически не может разойтись с историей. Товар в пути не
входит ни в один `on_hand`: каждая единица в каждый момент находится ровно в одном месте — на складе
отправления, в пути или на складе получателя (тест проверяет, что «на складах + в пути» не меняется).

**3. Одна команда — одна транзакция.** Отправка перемещения или FBO не имеет черновика: одна
команда атомарно списывает остаток с отправителя и создаёт операцию в пути. Остаток, операция и
запись истории пишутся в одной транзакции, при любой ошибке откатывается всё (есть тест).

**4. Блокировки против двойного списания.** Критичные операции берут строку остатка и строку
операции через `SELECT … FOR UPDATE` в едином порядке (операция → остаток), так что взаимных
блокировок нет. После ожидания блокировки значения читаются заново (`populate_existing`). Склад при
обычных операциях берётся на чтение (`FOR SHARE`), при архивации — на запись, поэтому склад не успеет
уйти в архив между проверкой и записью. Если PostgreSQL всё же прервёт операцию из-за deadlock,
API вернёт понятный 409 «повторите действие», а не 500.

**5. Повторное подтверждение безопасно.** Операция блокируется, читается её актуальный статус,
проверяется допустимый переход. Статусы идут только вперёд (`ACTIVE → CANCELLED | IN_TRANSIT`,
`IN_TRANSIT → RECEIVED`), поэтому повторная отправка или приёмка получает отказ «уже
отправлен / принята» и ничего не меняет. Проверено в том числе параллельными запросами.

**6. Нехватка на выбранном ФФ.** Отказ без единого изменения в базе. Другой склад автоматически
**не** выбирается: это решение менеджера. В сообщении показаны остатки на других ФФ: «Недостаточно
на «Север»: доступно 2, запрошено 5. На других ФФ доступно 6 (Юг 6); оформите перемещение».

**7. «Удалить» склад = архивировать.** ТЗ требует одновременно удалять ФФ и сохранять остатки и
историю, поэтому строка не удаляется, а получает `archived_at`. Архивный склад остаётся на экране
остатков, но на него нельзя оформлять новые операции. Допущения (не из ТЗ): склад нельзя
архивировать, пока на нём есть активные резервы FBS или к нему идёт перемещение (приёмку провести
было бы некуда); остаток с архивного склада **можно вывезти перемещением**, иначе он застрял бы
навсегда.

**8. Остатки меняются только операциями.** Прямой записи числа нет ни в интерфейсе, ни в API.
Для ошибок и пересчётов есть операция «Исправить остаток»: менеджер вводит фактическое количество и
обязательную причину, система сама считает разницу и пишет её в историю (`ADJUST_IN` / `ADJUST_OUT`).
Ниже резерва остаток опустить нельзя.

**9. Ограничения в базе, а не только в Python.** `on_hand ≥ 0`, `reserved ≥ 0`,
`reserved ≤ on_hand`, `quantity > 0`, допустимые типы и статусы, соответствие складов типу операции
(у перемещения разные склады отправления и назначения), `UNIQUE` и внешние ключи. Даже ошибка в
логике не позволит записать невозможное состояние.

**10. Скорость.** Читающие запросы не зависят от числа строк: остатки — 4 запроса (склады, товары,
остатки, «в пути»), история и список операций — по одному запросу с `JOIN` (тесты считают запросы).
«В пути» читается агрегатом по частичному индексу `WHERE status = 'IN_TRANSIT'`.

## Модель данных

| Таблица | Содержимое |
|---|---|
| `products` | артикул, название |
| `warehouses` | название, `archived_at` |
| `inventory` | (товар, склад) → `on_hand`, `reserved` |
| `operations` | тип (`RECEIPT`, `TRANSFER`, `FBS`, `FBO`, `ADJUSTMENT`), статус, товар, количество, склад отправления и назначения, причина |
| `events` | история: тип события, товар, количество, откуда, куда, время |

Резерв FBS — это операция типа `FBS` в статусе `ACTIVE`; `inventory.reserved` всегда равен сумме
активных резервов (тест сверяет). Одна операция — один артикул (см. «Ограничения»).

Статусы: резерв `ACTIVE → CANCELLED` или `ACTIVE → IN_TRANSIT` (отправлен клиенту);
перемещение и FBO `IN_TRANSIT → RECEIVED`; приход и корректировка сразу `RECEIVED`.

## Сверка остатков с историей

Показывает расхождения; на корректных данных ответ `0`.

```sql
WITH ev AS (
  SELECT product_id, to_warehouse_id AS wh, quantity AS d FROM events
   WHERE type IN ('RECEIPT','RECEIVE_TRANSFER','ADJUST_IN')
  UNION ALL
  SELECT product_id, from_warehouse_id, -quantity FROM events
   WHERE type IN ('SHIP_FBS','SHIP_TRANSFER','SHIP_FBO','ADJUST_OUT')
), calc AS (SELECT product_id, wh, SUM(d) AS s FROM ev GROUP BY 1, 2),
res AS (SELECT product_id, source_warehouse_id AS wh, SUM(quantity) AS r FROM operations
         WHERE type = 'FBS' AND status = 'ACTIVE' GROUP BY 1, 2)
SELECT count(*) AS mismatches FROM inventory i
  LEFT JOIN calc c ON c.product_id = i.product_id AND c.wh = i.warehouse_id
  LEFT JOIN res r ON r.product_id = i.product_id AND r.wh = i.warehouse_id
 WHERE i.on_hand <> COALESCE(c.s, 0) OR i.reserved <> COALESCE(r.r, 0);
```

## API

Swagger — `/docs`. Ошибки всегда в одном формате:
`{"error": {"code": "...", "message": "..."}}`, коды: `validation_error` (422), `not_found` (404),
`conflict` (409), `insufficient_stock` (409), `concurrent_conflict` (409), `internal_error` (500).
Числа принимаются строго как целые (`"5"`, `5.5`, `true` отклоняются).

Полный список методов — в Swagger. Чтение: `GET /api/stock`, `/operations/open`, `/history`,
`/warehouses`. Команды: `POST /api/receipts`, `/fbs/reservations`, `/fbs/{id}/cancel|ship`,
`/transfers`, `/transfers/{id}/receive`, `/fbo`, `/fbo/{id}/receive`, `/adjustments`, склады — под
`/api/warehouses`.

## Структура

Роуты в `app/api/routes.py` тонкие, вся бизнес-логика и транзакции в `app/services/` (`stock.py` —
приход, блокировки, нехватка; `fbs.py`; `shipments.py` — перемещения и FBO; `warehouses.py`;
`adjustments.py`; `queries.py` — чтение). Таблицы и ограничения БД — `app/models.py`, миграции —
`alembic/versions/`, интерфейс — `app/templates/` и `app/static/`, тесты — `tests/`.

## Допущения (не из ТЗ)

* Склад в архиве не принимает новых операций, но с него можно вывезти остаток.
* Архивировать нельзя при активных резервах и входящих перемещениях.
* У FBS нет приёмки: товар «у клиента» остаётся в пути (вручение в ТЗ не требуется).
* Магазин один, авторизации нет.

## Ограничения прототипа

* Операция относится к одному артикулу; поставка из нескольких артикулов оформляется несколькими
  операциями. Расширение до таблицы позиций (`operation_items`) возможно, но усложнит блокировки.
* Защиты от дубля при повторе запроса **создания** (`Idempotency-Key`) нет: повторное
  **подтверждение** защищено статусами и блокировками, этого требует ТЗ.
* Резерв отправляется целиком, без частичных отправок; возвратов нет.
* Нет авторизации, пагинации истории (последние N записей), реальных API маркетплейсов.

## Как использовался ИИ и как проверялся результат

ИИ (Claude Code) ускорил написание кода, тестов и интерфейса. Архитектурные решения (формула
остатков, «в пути» из операций, архивация вместо удаления, порядок блокировок) приняты и
проверены осознанно, а не принимались «как сгенерировано». Проверка:

* Сквозные сценарии ТЗ по шагам с проверкой сходимости остатков с историей после **каждого** действия.
* Конкурентные тесты на независимых соединениях PostgreSQL. Чтобы убедиться, что тесты вообще
  ловят гонку, я временно убрал `FOR UPDATE`: упала 5 из 9 конкурентных тестов, существовавших на
  тот момент (сейчас их 10), затем блокировка возвращена.
* Проверка в браузере, проверка данных напрямую в БД и после перезапуска сервера, SQL-сверка
  остатков с историей (выше).
* Повторный разбор кода после написания (его делал тот же ИИ, поэтому это самопроверка, а не
  независимое ревью): нашлось, что deadlock в БД превращался бы в голый 500, теперь это понятный
  ответ 409, есть тест.
